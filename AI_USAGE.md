# AI Usage — Best AI-Native Build

This file documents how AI was used to build **Quantum-Safe Certificate**, for
the QoreChain "Build Before Q-Day" Developer Fest special award **Best
AI-Native Build**. It is written honestly: an AI agent did the building, under
a human's direction.

## Workflow

- **Agent:** an AI coding agent (Muse Spark), working in a sandboxed VM under
  the direction of the project owner (GitHub: zawaproust).
- **How it worked:** the owner gave the goal in plain language ("enter the
  QoreChain hackathon, Quantum Pass track, build a quantum-safe certificate
  dapp"), and the agent researched the QoreChain docs, scaffolded the project,
  wrote the code, ran the tests and builds, and fixed the errors it found —
  reporting back at each milestone. The owner reviewed the plan, approved
  entering the hackathon, created the public GitHub repo, and makes the final
  submission decisions.
- **Tools used:** the QoreChain docs (docs.qorechain.io), `create-qorechain-dapp`,
  Foundry (contract tests), `npm`/`vite` (dApp build), the public testnet
  endpoints (read-only checks), and the QoreChain SDKs.

## What was generated by AI

- The `QuantumSafeCertificate` Solidity contract and its Foundry test suite
  (`contracts/`).
- The certificate feature in the React dApp (`src/App.tsx`, `src/certificateAbi.ts`):
  PQC status badge, EVM window status, mint flow, explorer links.
- The chain scripts (`scripts/`): account generation, PQC status check,
  ML-DSA-87 key registration, EVM window opening, contract deployment, and the
  hybrid-signed attestation transaction.
- This repo's docs (`README.md`, `BUILD_NOTES.md`, this file) and the MIT
  `LICENSE`.

## Human contribution

- The project idea, the track choice (Quantum Pass + Best AI-Native Build),
  and the decision to build a certificate dapp rather than a generic demo.
- The GitHub repo creation, the faucet claim (test QOR — needs the owner's
  dashboard sign-in), registration on build.qorechain.io, the demo video, and
  the final submission — all done by the human, because they need the owner's
  accounts.
- Review of the agent's reports at each milestone, including the call to keep
  the project minimal (one certificate per address, one hybrid-signed
  attestation) instead of adding features.

## Verification (what was actually run, not assumed)

- `forge build` + `forge test`: 4/4 tests pass (mint/read, one-per-address,
  bad attestation, no-certificate default).
- `npm run build`: typecheck + Vite production build pass.
- `node scripts/pqc-status.mjs`: reads the real deployer account on the live
  testnet (balance 0, PQC not registered, no window) — the faucet blocker is
  real and documented in `BUILD_NOTES.md`, not worked around.
- No transaction was faked: the contract address and attestation hash are
  marked *pending* in the README until the deploy actually runs on testnet.
